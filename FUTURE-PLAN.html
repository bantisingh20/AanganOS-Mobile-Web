AanganOS — Future Plan & Roadmap

Resident + Admin single app (React + Capacitor, shadcn/Tailwind). Backed by the .NET API & shared menu/permission model.

One codebase: packages/app (mobile) + packages/admin (web) + packages/shared Permission hook: usePermission(key) Backend menu: surface-filtered & permission-filtered
Decision already answered — yes, one single app works for both resident & admin personas.
  • App & admin already share one AuthContext, API clients, permission model and i18n.
  • Backend aggregates ALL of a user's roles and their combined permissions into one token at login (ResolveAuthorizationAsync). There is no per-role token today.
  • So screens adapt from usePermission() + the backend menu. Admin screens that already exist (announcements, helpdesk, visitors, amenities, maintenance billing, residents, towers/units) can be surfaced in-app without a second app.

1 Home & Services from the backend menu NEXT

Goal

Stop hardcoding Home quick-tiles and Services tiles. Each tile comes from the backend menu (GET /api/v1/menu, Surface.App), already permission-filtered server-side. Layout stays the same (3 bottom tabs: Home · Services · Profile); only the tile contents become dynamic.

What already exists

  • GET /api/v1/menu returns a permission-filtered, surface-aware tree (MenuService.GetMenuAsync).
  • useMenu() hook in shared already fetches it.
  • 10 Surface.App menu items are seeded (home, services, invite-visitor, my-visitors, approvals, parcels, helpdesk, announcements, profile, visitors group).

Work to do

  1. Render Home tiles + Services from useMenu() instead of the hardcoded arrays in DashboardTab / ServicesTab.
  2. Add two small app-side maps: ROUTE_MAP (menu route-name → web path, e.g. inviteVisitor → /invite-visitor) and ICON_MAP (menu icon name → lucide icon). Unmapped routes are skipped gracefully.
  3. Seed missing default App menu items in the DB so residents get: My Profile, My Household, Maintenance, Daily Help (recurring). These carry RequiredPermissionResource + actions so they only show when permitted.
  4. Keep bottom tabs fixed; group menu nodes under Home vs Services by parent key (app.home children vs app.services children).
Note: per-role defaults live in menu seed data (backend MenuItems), not hardcoded in the app. "Security" defaults can be seeded, but their screens aren't built in this web app yet (see §3).

2 Multi-role per user + in-app role switch MAJOR

Requirement

One resident can hold multiple roles (Resident, Security, CommunityAdmin, OrganizationAdmin). They log in with their default role; in Profile they can switch role, and the switched role reveals extra screens/actions. Resident features stay as-is; everything else is layered on by role.

Backend reality (important)

  • Login already returns all role names + the union of all their permissions in one token. There is no switch-role / active-role endpoint today.
  • So "switch role" is, by default, a client-side active-role filter over menu + usePermission — not a backend re-auth.
Decision needed before building:
  • Option A — client-side active role (fast): store a chosen "active role" locally; filter the menu/tiles and the permission hook to that role's scope. Token unchanged. Quick, no backend change. Weakness: not a hard security boundary (token still holds union of permissions).
  • Option B — server-issued per-role token (strict): add a POST /api/v1/auth/switch-role that re-issues a token scoped to the selected role. Proper isolation; needs backend work + refresh wiring.
Recommendation: start with A for UX now, move to B if strict isolation is required.

Work to do

  1. Add an active-role concept in AuthContext (default = the user's primary role); persist the choice.
  2. Profile → a "Switch role" picker listing the user's roles (from user.roles).
  3. Make usePermission() and the menu render respect the active role (filter to that role's granted permissions for Option A).
  4. Default-role mapping: Resident → resident tabs; Admin roles → admin screens surfaced in-app.
  5. (If Option B) backend switch-role endpoint + token refresh.

§4 Resident Notices wall (community wall, resident-writable)

A separate, resident-writable notices board (distinct from the admin Announcements board). A resident posts a short notice (e.g. "water off tomorrow due to tank cleaning"). Chosen approach: Option C.

Approval: a per-community config flag decides whether resident notices need admin approval. If approval is ON: a new notice is pending (visible only to its author) until an admin approves; once approved it is visible to all residents of that community. If OFF: the notice is visible community-wide immediately.

Open decisions (confirm before building):

  • Backend support: no resident-authored-notice entity/endpoint exists yet (not verified in depth). Needs a new ResidentNotice entity + migration + controller + permission resource (e.g. ResidentNotice with View/Create and Approve for admins). This is a DB/schema + API change — needs explicit go-ahead.
  • Approval source: per-community config flag vs always-on vs always-instant.
  • Rejected notice: hidden with a reason shown to the author?
  • UI home: new tile/route /resident-notices, separate from admin Announcements.
  • Who posts/moderates: any verified resident posts; admins approve/reject.
